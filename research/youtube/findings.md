# Research: YouTube anonymous extraction feasibility (issue #4)

Date: 2026-10-16. Method: light anonymous probes (1× oEmbed, 2× watch HTML, 2× Innertube player POSTs) with plain fetch, no auth. Test video: `aqz-KE-bpKQ` (Big Buck Bunny).

## Verdict: INFEASIBLE with Bun-native plain fetch alone

No login, no API keys, no yt-dlp → no reliable direct-MP4 URL. Getting one today requires yt-dlp-class machinery (client spoofing, signature decipher, PO-token minting, rotation past bot-checks) — explicitly out of scope for this app's server-side plain-fetch resolver.

## oEmbed verdict: CONFIRMED metadata-only

`GET youtube.com/oembed?url=...&format=json` returns exactly: `title, author_name, author_url, type, height, width, version, provider_name, provider_url, thumbnail_height, thumbnail_width, thumbnail_url, html`. No media/download URL field exists (`url`/`media_url` absent). The `html` field is just an `<iframe>` embed. Useful for titles/thumbnails, useless for MP4 resolution.

## Signature / progressive-stream path reality

1. **Watch-page HTML** (`/watch?v=...`, browser UA, `playabilityStatus: OK`) still embeds `ytInitialPlayerResponse.streamingData`, but: `formats` (progressive A+V) is **empty**, and **0 of 40 `adaptiveFormats` carry `url` or `signatureCipher`** — entries are metadata only (itag, mimeType, bitrate, ranges, contentLength). The classic signature-decipher path is therefore not just obfuscated, it is **absent from the static page**.
2. **SABR-only delivery.** The only playback URL present is `serverAbrStreamingUrl` (Server-side Ad-Bound Streaming). Resolving actual media segments requires POSTing to it with a Protobuf request, a valid **PO token** (BotGuard attestation, generated by running Google's JS challenge — needs JS execution + fresh tokens per session), and usually logged-in or consented cookies.
3. **Innertube `player` endpoint (anonymous):** `ANDROID_TESTSUITE` client → HTTP 404 (dead client); `WEB` client without PO token/cookies → `UNPLAYABLE / Video unavailable`, no `streamingData`. Known-good clients rotate constantly and old bypasses die — exactly the treadmill yt-dlp exists to ride.
4. **PO-token / bot-check summary:** PO tokens are short-lived attestations minted by BotGuard JS; datacenter IPs get challenged or served `UNPLAYABLE`; tokens cannot be minted with static fetch — they need a JS runtime executing obfuscated, frequently-changing code. This is the concrete blocker, not deciphering per se.

## Reliability if attempted anyway: ~zero as a product feature

Even if a hack works today (e.g. a currently-whitelisted Innertube client + decipher), breakage cadence is weeks-to-months, failures are silent (`UNPLAYABLE`, 403 on googlevideo with expired `expire=`), and Shorts/age-restricted/region-gated items fail first. Not shippable for best-MP4 auto-pick.

## Shorts coverage

Moot given the verdict, but for the record: Shorts (`/shorts/<id>`, `youtu.be`, `/watch`) share the same 11-char video-ID namespace and the same player/SABR pipeline — whatever works for `watch` works for Shorts. No separate path needed.

## ToS note

YouTube ToS (§4) prohibits accessing content except through the provided players/APIs; direct-stream extraction violates it and googlevideo URLs are signed/expiring per-IP, so server-side fetch-and-cache is both ToS-hostile and technically brittle. oEmbed + official embeds are the compliant path.

## Recommendation

Re-rank YouTube out of the anonymous batch: keep oEmbed for metadata (title/author/thumbnail), do NOT promise MP4 download; point users at the watch page / official embed. If YT support is ever required, the only honest option is delegating to yt-dlp (server-side binary, separate service) — a product decision, not a fetch tweak.

## Open questions (none blocking)

- Whether a logged-in-cookie path is acceptable is a product/ToS call, not researched here.
- Cobalt API / Piped-style proxies were not evaluated (third-party dependency, same ToS shadow).
